# 隐私设计

这类工具碰的是**通知、使用时长、健康、日程** —— 最敏感的那一类数据。所以规则先定死：

## 三条硬规则

**1. 原始数据只留在你自己的服务器上**
不经过任何第三方。中枢是单文件 Python + SQLite，你可以随时 `sqlite3 hub.db` 看里面有什么。

**2. 给模型的一切先脱敏**
`hub.py` 里有一道**强制关卡**，进模型的上下文必须过它：

| 原始 | 脱敏后 |
|---|---|
| 通知原文 | 只剩数值 + 小时级时间（"14时"） |
| 日程标题（"去校医院看牙"） | 只剩类型（"其他事项"） |
| App 名（哔哩哔哩） | 只剩分类（"短视频/视频"） |
| 课程名 / 教师 / 教室 | 只留"第几节 + 上课" |
| 睡眠 327 分钟 | 330 分钟（半小时粒度） |
| 设备名 | "手表 / 手机 / 电脑" |
| 待办内容 | 只给条数 |
| 进程名 / 窗口标题（电脑侧） | **一概不给**；只给"换了多少次窗口"这个次数 |
| 磁盘 / 内存（电脑侧） | 只给百分比，不给路径、不给文件名 |
| 基线对比（"比平时多 42%"） | 只给**类别名 + 百分比**；不给 App 名、不给历史序列、不给具体日期 |

**能核对**：`GET /llm-preview` 会返回"模型这一轮到底会看到什么"，以及"模型永远看不到什么"。
自己先看一眼，再决定放不放行。

**2.5 你自己的设备看到的是原值**
`/today` 里的 `care` 块（挂件/网页用）**不做模糊化** —— 电量就是 34%、歌名就是歌名、磁盘就是剩 12%。
理由：那是**你自己的数据、你自己的设备**，同一把 token 才能取；它和"给模型看的那份"是**两条不同的路**。
模型那一路永远走上面那张表。想核对差异：`GET /llm-preview` 看模型那份，`GET /today` 看你那份。

**3. 密钥不上服务器**
中枢只有自己的 `token`；**模型 API key 只留在"说话层"所在的那台机器上**。
中枢连模型都碰不到 —— 它只会产出结构化事实。

## 传输与存储

- **库文件加密**：SQLite 不加密（拿到文件即全部历史）→ 用 `hubctl backup --encrypt` 或整盘加密
  ```bash
  gocryptfs ~/whale-enc /root/hub     # 目录级加密（示例）
  # 或给云主机加一块 LUKS 数据盘，把 /root/hub 放上去
  ```
- **保留策略**：`privacy.retention_days`（默认 365）自动清理；`0` 永久保留
- **传输**：HTTPS + **证书固定**（App 里只信任你那一张证书）；私钥在服务器本机生成、`chmod 600`、**永不外传**
- **本地队列**：Android Keystore AES-256-GCM 加密；取不到密钥时**降级明文但不丢数据**（安全不能以"传不上去"为代价）
- **明文**：`network_security_config.xml` 里 `cleartextTrafficPermitted="false"`，App 不会明文外发

### 外发路径之一：直发出口（文本，v0.1.17 起；现有 8 个）

除了"说话层 → 网关 → 微信"这条主路，中枢自己还能直发（`POST /push`）：企业微信群机器人 /
通用 webhook / ntfy / Bark / 钉钉 / Discord / QQ 官方机器人。**它是一条数据离开这台机器的路，所以规矩写死**：

- **默认是空的**：`channels` 不配置就完全没有这个出口（`GET /channels` 会明确回"空"）。
- **绝不自动使用**：它没有接进决策闭环，只有显式调用 `POST /push` 才发送（避免和说话层重复推送）。
- **发给谁要说清**：走企业微信 = 内容交给腾讯的服务器；走通用 webhook = 交给**你自己**搭的那个服务。
  两者都**不经过**本项目的任何服务器。
- **地址本身就是凭据**（webhook URL 里带 key）→ 出口状态接口只回"已配置/空"，**从不打印地址本身**。
- 发送动作会落审计（`channel_send`，只记"发了一条 N 字"，不记内容）。

### 外发路径之二：分析出口（数据，v0.2.0 起）

第 9 个出口**不发货话，只发数据**：让 AI 分析处理数据之后，把**分析结果本身**（结构化 JSON）
送到 `channels.analysis_webhook` / `analysis_file`，或由消费者自己 `GET /analysis` 拉。
它比文本出口多一条规矩，因为它会**把数据交给模型处理**：

- **输入不新增**：分析只读 `/llm-preview` 的那份**脱敏上下文**（没有通知原文、App 名、
  分钟级时间、定位）。分析出口**不会**成为绕过脱敏闸的第二条管道 —— 这是设计上的硬边界，
  不是"我们很小心"。核对方式：`curl /llm-preview` 看到的 `would_send_to_model`
  与 `what_model_never_sees`，就是它能看到与看不到的全部。
- **输出可溯源**：产物里每个指标 `id` 必须与那份上下文里的键**逐字相同**（写端强制、找不到就丢），
  所以不会有"看起来像数据的编造值"。数值对不上上下文会被标 `unverified=true`，
  读端应视作弱证据。
- **输出不许成句**：所有字符串只能是短标签（≤24 字、不含句读），防止"数据出口悄悄退化成聊天"。
  规范见 [`ANALYSIS-FORMAT.md`](ANALYSIS-FORMAT.md)。
- **格式硬门禁**：不合规的 payload 被**拒收**（不落库、不分发），并写一条 `analysis_reject` 审计。
  落库的是 `analyses` 表（默认只留最近 50 份，`channels.analysis_keep` 可调），只存分析结果本身。
- **出口状态单独列**：`hubctl channels` 会把分析出口与 8 个文本出口分开报 ——
  配了它**不会**让她多说话，也不会占用提醒额度。

## 收到的人该注意

- 中枢**别对公网敞开**：至少 token + 防火墙只放行你自己的 IP + HTTPS
- 采集器是**私有自用 App**：别上架（无障碍/通知监听类权限本来就上不了架）
- 想给别人用？让每个人自己部署一套 —— 不要做一个"共用的中枢"

## 分发与加固（自测后补的）

**分发服务器只发白名单目录。** 用来分发 APK/脚本的那个小服务**不能对公网敞开整个工作目录** ——
里面可能有含明文密码的脚本、配置文件、别的项目源码，知道文件名的人就能下载。
**只放一个 `pub/` 白名单目录出去**：

```
curl http://.../hub.py            # ✓ 该发的能下
curl http://.../hub.json          # 404（配置不外发）
curl http://.../devpw.sh          # 404（含密码的脚本不外发）
```

**中枢自身的加固**（安全自测后加的三条）：
1. **只认 `X-Token` 请求头** —— 不再接受 `?token=`（query 里的 token 会进服务器日志、
   也会留在浏览器历史和代理记录里）
2. **单请求体积上限 1MB** —— 超大包直接拒掉（否则一个大包能把内存吃光）
3. **每个来源 240 次/分钟** —— 够用就好的限流，防"被刷"

## 一轮外部锐评之后补的（逐条对应）

| 批评 | 是否成立 | 处理 |
|---|---|---|
| 中继默认不校验证书 | ✅ 成立 | 改成"不给 CA 拒绝启动"，`WHALE_INSECURE=1` 仅调试 |
| 原始明文会落库 | ✅ 成立 | `privacy.store_raw_text` 默认 **false**：健康通知原文不再入库 |
| 防火墙没收口 | ✅ 成立 | 明文端口已从公网撤掉，只留 HTTPS；建议再上 VPN/Tailscale |
| SQLite 明文，文件拿走就全裸 | ✅ 成立 | 提供 `backup/dump --encrypt`（AES-256）；建议整盘加密（LUKS / gocryptfs）|
| 采集端被篡改就能上报任意内容 | ✅ 成立（无法根除）| 应用层脱敏只保证"给模型的那份"干净 |
| MCU 链路没有重试/校验 | ✅ 成立 | 协议加 `s=`/`c=`，中继落盘补发 |
| 单文件会难维护 | ✅ 成立 | 有意为之（部署=拷一个文件）；后续再拆 |
| 高并发/没有队列扛不住 | ⚠️ 过头 | 个人场景一天几百次请求，限流档位 240 次/分钟，差三个数量级 |
| SQLite 撑不住多年时序 | ⚠️ 过头 | 约 1000 行/天 ≈ 35 万行/年，SQLite 百万级无压力 |

## 自测覆盖：鉴权（无/错 token）、参数滥用（超大 limit）、SQL 注入、路径穿越、
大 payload、方法滥用与堆栈泄露、TLS 证书固定、webhook 签名与重放、分发源目录穿越、直发出口（桩服务器逐字校验 payload）。
结论：鉴权/注入/穿越/重放/TLS 全部通过；分发源泄露与无限流是**当时真存在的两个洞，已修**。

**最近一轮复测（22 项）**：又发现一处**报错信息泄露服务端路径**（401 会把 `hub.json` 的绝对路径
回给未授权方）—— 已改成中性文案。同时确认：>1MB 的请求回 `413`、metric 名里塞 SQL 被安全处理、
分发口 10 种路径穿越写法全部 `404`、`/api/mcu` 的 query token 只对它自己有效。
